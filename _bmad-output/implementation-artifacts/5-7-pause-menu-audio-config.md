## Story

As a player,
I want pausing to open a menu where I can set volume and turn sound on or off,
So that the mix is controllable without knowing hidden key shortcuts. (Added by the readiness audit 2026-11-07, decision D-006; the config UI should have shipped with the v1 audio layer — the mechanism is complete, only the surface is missing. `epics.md:853-877`.)

## Acceptance Criteria

(verbatim from `_bmad-output/planning-artifacts/epics.md:853-877` — FR30, FR27, FR24, FR22, NFR6, NFR7)

**Given** a paused run (P/Esc or tab-hide)
**When** the freeze frame holds
**Then** a menu presents Resume plus a volume control and a sound on/off toggle, initialized from the live persisted settings at open (FR30, FR27)

**Given** the volume control or the sound toggle
**When** the player uses it
**Then** it calls the existing seams only — `audio.setVolume` / `audio.toggleMute` — persisting through the existing storage path; no new audio plumbing and no second persistence path (FR24; shared-handler rule)

**Given** the menu is open
**When** the player clicks or keys anything
**Then** no jump arms, no run starts, and nothing resumes until Resume is chosen — the freeze-frame input lock holds behind the menu (FR22 handler hygiene, D-12 lineage)

**Given** the keyboard shortcuts (`Mute` key, `-`/`=`) fire while the menu is open
**When** settings change
**Then** the menu controls re-render in sync with the new state — one source of truth, no drift (FR30)

**And** the panel lands inside the existing letterbox resize path (NFR7), stays shell-only and static-file-only (NFR6), the sim import graph is unchanged (`tests/boundary.test.js` green), and the panel is built so a later idle-screen entry point can reuse it without rework (reuse sanctioned, not required here)

## Decisions (baked — `[DECIDED-BY-CREATE]`; do not re-litigate at dev time)

- **D1 — DOM shape & placement: one panel div appended under `#hud`.** `setupMenu` creates `div.hud-menu` and `hudRoot.appendChild(wrap)` — the trailing-append sibling of the cards strip (`:463-465`) and the marker (`:96-105`), so the DESIGN HUD slot order (marker between pips and owned, pinned by `ceilingmarker.test.js:343-350`) is untouched. Positioning mirrors the cards precedent exactly — `.hud-menu { position: absolute; left: 0; right: 0; top: 40%; … }` inside `#hud`: `#hud` itself is the `inset:0` overlay the letterbox path already carries (`.hud-marker` rides it in-flow `css/style.css:91-94`; `.hud-cards` rides it absolutely `:47-60`) — this IS the letterbox path NFR7 names (`applyWindowSize` `shell.js:45-53` sizes the canvas box; the HUD overlay has always been viewport-absolute inside `body`'s grid). Do NOT add per-band geometry math to the menu; that would be the layout bypass NFR7 forbids. Children (built once at boot, updated by signature — cards idiom `:529-547`): `.hud-menu-btn.menu-resume` (`Resume`), a `.hud-menu-row` with `.hud-menu-btn.menu-vol-down` (`-`), `.hud-menu-read` (`volume 70%`), `.hud-menu-btn.menu-vol-up` (`+`), `.hud-menu-btn.menu-mute` (`Sound on` / `Sound muted`); hidden state is the class `hidden` (`display:none` — static, no transition). `#hud`'s `pointer-events:none` (css `:22`) stays; every button re-enables `pointer-events:auto` (cards idiom css `:58/:62`). The panel inherits `#hud`'s `aria-hidden="true"` from frozen `index.html:18` — noted, accepted, out of scope for a demake with a frozen index (do not "fix" it by editing index.html).
- **D2 — Controls are div+click, not `<input>` elements.** The harness stubs drive `.fire(type, ev)` on registered `addEventListener` listeners (`pickerhud.test.js:50-51`) and the frozen cards legs prove that shape end-to-end; a `<input type="range">`/`checkbox` would need `change`-event plumbing no stub fires and would make the live-browser lane the ONLY proof of the Node-facing behavior. The click targets ARE the buttons (`<button>` adds focus/tab-order semantics this story must not introduce — see D5's no-new-input-surface law); `pointerdown` handlers guarded by the visible callback (cards guard by status, `:516`). 44px+ targets per the cards CSS note (`css/style.css:43-46`).
- **D3 — Sync law: the menu is a VIEW of `audio`'s settings, rendered from the SAME updateHud frame path — no second call site, no local mirror.** `updateHud` grows `if (menu) menu.render();` beside `if (cards) cards.render();` (`:598`); `render()` READS `audio ? {audio.getVolume(), audio.isMuted()} : diag` and the `api.visible()` callback every frame and writes text/className under the signature guard. Justification: (a) `updateHud` already runs every rAF frame INCLUDING during the freeze (`:712-714` + Context §1) — zero new clocks/timers (NFR8) and the panel is refreshed by the exact path that keeps the freeze frame alive; (b) an "explicit render on every seam" design would be a per-path call fork — banned by the shared-handler rule (AGENTS.md:53) and one forgotten seam (boot persistence load, `audio-error`, OS Mute key) away from AC4 drift; (c) `setVolume`/`toggleMute` return nothing (`audio.js:223-231`), which makes read-after-write the only correct protocol — the frame render IS the read-back. Menu open/close is therefore also just rendered state: `visible` = `api.visible()` = `() => paused` at the pause call site; nothing in the menu flips anything else.
- **D4 — `setupMenu(root, api)` is a module-level factory (sibling of the DOM-layer code) with NO pause-specific capture** — AC5's reuse clause made concrete. `api = { visible(), volume(), muted(), diag(), onResume(), onVolume(delta), onToggleMute() }`; the factory owns DOM + guards only; every semantic is a callback the caller supplies. `startGame` wires `visible: () => paused`, `volume: () => audio?.getVolume()`, `onResume: () => resumeFromPause()`, `onVolume: bumpVolume`, `onToggleMute: () => audio?.toggleMute()` — built at boot with the same `hudRoot` probe as cards (`:88-89`; `audio` may still be null at boot — the callbacks read it live, never capture it). A later idle-screen entry passes `visible: () => idleMenu` and its own `onResume: startFreshRun`-side callback without touching the factory. The factory NEVER touches `run`, `paused`, `holdFrom`, or any shell transition variable directly — provable by grep (L5 leg), which is the AC3 fence made structural.
- **D5 — Keyboard: ZERO new bindings.** `-`/`=`/`Mute`/`P`/`Esc` keep their shipped behavior; they already fire while paused because the audio short-circuits precede the pause toggle (`shell.js:278-288`) and `press`/`release` are the only paused-guarded paths (`:195/:201`) — AC4 exists to PIN that, not to change it. Menu navigation keys (Tab/arrows/Enter) are REJECTED: focus plumbing is new input surface (FR22 audit burden, D-12 lineage) for a canvas game whose mouse/touch layer the cards already proved, and P/Esc already resumes from the keyboard. The one shared handler: `const VOLUME_STEP = 0.1` + `function bumpVolume(delta) { if (audio) audio.setVolume(audio.getVolume() + delta); }` in `startGame`, used by the `-`/`=` keydown lines (`:279-280`, replacing their inline arithmetic — behavior-identical because `setVolume` clamps at `audio.js:224` and `getVolume` is always finite) AND by both menu buttons. `delta` sign only; clamp lives in `setVolume` (one truth).
- **D6 — Resume law (the exact anti-hole): the resume handler body is `onResume()` → `resumeFromPause()` and NOTHING else.** It must NOT copy the cards' pointer wiring — cards call `unlockAudio()` on pointerdown (`:518`) and `release()` on pointerup (`:523`) because their semantics ARE gesture semantics; the menu's are not. `resumeFromPause` already routes the audio-context resume (`:262`) and the D-07 lead-in (`:256`).
