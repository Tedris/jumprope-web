# Story 3.3: Steel Cord — charges that survive one trip

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a builder,
I want some ropes armored against a single trip,
So that HP purchases carry insurance and trip decisions gain a second layer.

## Acceptance Criteria

1. (AC1) **Steel Cord pick → one rope gains a charge, as run-record data.** `reinforce` becomes run-shaped (`shape: 'run'`, dispatched by the shipped `patchedRun` — ADR-2, `js/game.js:220-226`); its apply writes the new sibling field `run.charged` = **count of held charges, 0–2** (a scalar, per D-a — deliberately untethered from `run.ropes`: charges are a counter the run holds, not per-rope flags; code review 2026-11-08). `createRun()` gains `charged: 0` — charge state is part of the record, not a side-channel. At most 2 charges simultaneously, enforced three ways: `owned` cap 2, `stateCap { charged: 2 }` hide (already shipped, `js/upgrades.js:42`), and a defensive `clampCharged` write in `patchedRun`'s run-shaped arm — applying to a crafted record at 2 (or with `charged: Infinity`) stays at 2: data, not error (FR12).
2. (AC2) **A trip through the rope branch with a charge consumes the charge instead of stripping a rope.** Resolution order is **buffer → charge → strip** (epics.md:549; the architecture waterfall `game-architecture.md:251`): the new branch sits strictly between the buffer branch and the `ropeCount > 1` strip branch in `tickRun` (`js/game.js:141-170`). Ropes are untouched; the blank spans exactly one revolution — `iframesLeft = ropeCount` (unchanged count × the GDD rule "i-frames last one pass per rope held", gdd.md:174-176); the streak zeroes (Story 1.4 chain-break policy, D-e); the failing crossing scores nothing. Events: `chargeUsed` only — **no `ropeLost`, no `trip`** (D-f). i-frame mechanics are untouched: the strip path's `iframesLeft = ropeCount - 1` and the blank's pass-through stay exactly as Story 1.2 shipped them (FR2 interlock).
3. (AC3) **A trip with no charge is byte-identical Epic 1 behavior.** `tests/tripresolution.test.js`, `tests/multirope.test.js`, `tests/v1parity.test.js` pass UNMODIFIED — that is the proof; records without the field (`charged` absent/invalid) behave as uncharged (the `clampCharged` read-heal — its nullish/min arms cover absence, no `?? 0` in the tick read; the module's invalid-states-are-data doctrine, FR2 protected).
4. (AC4) **At the last rope, the charge is the difference between life and death** (explicit test leg, epics.md:555): `ropes: 1` + `charged: 1` → trip consumes the charge, status stays `running`, ropes stay 1, the run continues through the one-revolution blank. The same rig at `charged: 0` still dies (`status 'over'`, `outcome 'tripped'`, `trip` event) — contrast pair leg (FR2, FR12).
5. (AC5) **The deal site reads live charge state** — the `charged: 0` literal at `js/game.js:132` becomes the clamped live value (`deferred-work.md:85` owned this wiring; `:86` confirmed the arm is 3.3's). Witness: a crafted `{ owned: { reinforce: 1 }, charged: 2, skips: 9 }` ticked to the 10th skip with seeded rng deals an offer that EXCLUDES `reinforce`, while the same seed at `charged: 0` includes it (same-seed contrast — falsifies "forgot the wiring"; the pure seam already pins the `stateCap` arm in `tests/offerstate.test.js`).
6. (AC6) **Re-contracts are exactly the two sites in Task 5** — every other existing test file byte-identical, proven with `git diff 79ba9ec -- tests/` in the Debug Log (NFR5). New behavior ships in the new file `tests/steelcord.test.js` with red-green mutation-proven legs (Epic 1 retro A3). Suite green < 10 s wall (baseline 318/318 @ ~8.5 s).

- **D-a — `run.charged` is a scalar count (0–2), not a per-rope array or ordered rope-list.** The shipped rope model is a count with degenerate slot identity — all ropes share one clock at even offsets, strip is "any rope" (`js/game.js:152-155`). The architecture's `ropes: [{ mul, charged }]` was never built (3.2's note); its `charged`-lives-in-the-run-record intent ("not a side-table", game-architecture.md:230) transfers faithfully to a sibling scalar field. FR14's "cord charges per rope" for Story 3.5 is satisfiable as `charged` count + rope pips — per-slot identity has no visible surface anyway (one rope is drawn in 3D until 5.3, `deferred-work.md:73`). The counter is deliberately UNTETHERED from `run.ropes` — a one-rope run may legitimately hold 2 charges (code review 2026-11-08: binding `charged ≤ min(ropes, MAX_CHARGED)` would make the clamp ropes-dependent with no shipped precedent; whether 2 charges at one rope is over- or under-powered is Story 6.1's balance call).
